## 0. תקציר מנהלים (Executive Summary)

סוכני הביטוח והפנסיה בישראל עובדים היום על מערכות דור ישן (עתיד, Surense, אלמגור ודומיהן):
Desktop/Client-Server, UX מיושן, קליטת מסלקה חלקית ידנית, ומסמכי הנמקה שמורכבים ב-Word
ונשלחים לחתימה בפקס/מייל. התוצאה: **תהליך מכירה של 3–7 ימים, חשיפה רגולטורית גבוהה, ואפס
יכולת אכיפה של תקינות ההנמקה.**

ה-MVP של PensionOS מתמקד **אך ורק** בשרשרת הליבה, מקצה לקצה:

```
קליטת נתונים (מסלקה + הר הביטוח)  →  תיק לקוח 360°  →  מסמך הנמקה תקני  →  חתימה דיגיטלית נעולה
```

**יעד המוצר:** לקצר את הזמן מ"בקשת מידע במסלקה" ועד "מסמך הנמקה חתום ונעול" מ-3–7 ימים
ל**פחות מ-45 דקות עבודת סוכן**, תוך יצירת "תיק הוכחות" (Evidence Package) שמגן על הסוכן
בביקורת רשות שוק ההון.

### עקרון האדריכלות המרכזי — Immutable Snapshot

הלב של המערכת אינו ה-UI אלא **קיבעון הנתונים**: כל מסמך הנמקה נקשר ל-`portfolio_snapshot`
בלתי-משתנה (immutable), עם `sha256` על גבי הנתונים ששימשו להמלצה ועל גבי קבצי ה-XML הגולמיים.
מסמך חתום לעולם לא "מתעדכן" — הוא נעול, חתום ומאוחסן ב-WORM.
זהו ההבדל המהותי בין מערכת CRM לבין מערכת שעומדת בביקורת.

### מדדי הצלחה ל-MVP (Success Metrics)

| מדד | יעד MVP | שיטת מדידה |
|---|---|---|
| Time-to-Signed-Doc | < 45 דק' עבודת סוכן, < 24h מקצה לקצה | טלמטריה על `interactions` |
| שיעור פענוח XML מוצלח | ≥ 97% מהקבצים ללא התערבות ידנית | `parse_jobs.status` |
| שיעור סיום חתימה (Completion) | ≥ 80% מהמסמכים שנשלחו נחתמים תוך 72h | `signature_envelopes` |
| שגיאות רגולטוריות בבדיקת ציות | 0 מסמכים ללא שדות חובה | Compliance Linter (חוסם) |
| P95 זמן פענוח תיק מלא | < 90 שניות מרגע הורדת הקבצים | APM |
| NPS סוכנים בפיילוט | ≥ 40 | סקר בסוף פיילוט |

## 1. היקף ה-MVP (Scope)

### 1.1 בתוך ה-Scope

| # | רכיב | תיאור תמציתי |
|---|---|---|
| **A** | **Data Ingestion Engine** | אינטגרציה למסלקה הפנסיונית (בקשה → Polling → הורדה), פענוח XML "ממשק אחיד", נרמול לקנוני, קליטת נתוני הר הביטוח |
| **B** | **תיק לקוח 360°** | פרטים אישיים ומשפחתיים, נכסים פנסיוניים, פיננסיים ופוליסות פרט, כיסויים, דמי ניהול, מוטבים |
| **C** | **מחולל הנמקה** | Rules Engine + מחולל PDF תקני לפי תקנות פרטי מסמך הנמקה, כולל השוואת דמי ניהול/כיסויים ואזהרות ניוד |
| **D** | **e-Sign** | שליחה ב-SMS/WhatsApp, אימות זהות OTP, חתימה בנייד, חתימת PAdES + חותמת זמן, נעילה ל-WORM |

### 1.2 מחוץ ל-Scope ב-MVP (במפורש)

כדי לשמור על מיקוד, הפריטים הבאים **אינם** ב-MVP וייכנסו ל-Roadmap:

- ❌ ממשקי הפקה/הצטרפות (ממשק "פניות לגוף מוסדי", ממשק שינויים) — ידני מחוץ למערכת
- ❌ ניהול עמלות, מודל תגמול וסליקת עמלות סוכן
- ❌ CRM מלא: משפך שיווקי, אוטומציות, קמפיינים, דיוור המוני
- ❌ אפליקציית לקוח קצה (Client App) — רק פורטל חתימה חד-פעמי
- ❌ תכנון פרישה אקטוארי, סימולטור מס, אופטימיזציית משיכות
- ❌ ניהול תביעות ותפעול שוטף
- ❌ מודולי ביטוח אלמנטרי (רכב/דירה/עסק)
- ❌ ריבוי מטבעות / פעילות מחוץ לישראל
- ❌ AI Copilot גנרטיבי לניסוח הנמקות (ראה §1.3)

### 1.3 החלטה מודעת: אין LLM בנתיב ההנמקה ב-MVP

מסמך ההנמקה הוא מסמך משפטי-רגולטורי. ניסוח נימוקים ב-LLM יוצר סיכון הזיה, אי-דטרמיניזם
וקושי בהגנה בביקורת. לכן **ב-MVP כל טקסט ההנמקה מופק מ-Rules Engine דטרמיניסטי + תבניות
מאושרות ע"י יועץ ציות**. LLM ייכנס ב-Phase 2 בשני מקומות בלבד, שניהם מחוץ לנתיב הקריטי:
1. **סיוע במיפוי שדות XML חריגים** (הצעה למיפוי, אישור אנושי חובה).
2. **סיכום שיחה/פגישה חופשי** בתוך `interactions` — לא נכנס למסמך.
